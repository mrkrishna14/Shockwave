# demo/reports — generated demo output

Everything here except this README and `.gitkeep` is generated by
`.venv/bin/python demo/scripts/demo.py <command>` and deleted by `demo.py reset`. Git ignores it.
The checked-in reference copy of the normalized results is `demo/expected/results/`. A test
(`tests/demo/test_demo_pipeline.py`) runs `demo.py all` into temporary directories and checks that
the fresh `results/` is byte-for-byte identical to it.

Labels that apply to every file:

- **Simulated change.** The proposed Stripe change is SIMULATED. Stripe has not announced or
  proposed it. Stripe is not a Shockwave customer and has not endorsed Shockwave.
- **Fixture server.** The fixture server and the scenario harnesses simulate Stripe responses
  from `demo/stripe-fixtures`. They are not Stripe.
- **Runs.** Runs use the LOCAL RUNNER DOUBLE: trusted local fixtures, a plain subprocess, not a
  sandbox, and not Sai's runner. The consumers' own suites run the same way.
- **Analysis.** Analysis is deterministic rules (`analysis_mode: rules`), with no LLM.
- **Dependencies.** Consumer dependencies come from the labeled FIXTURE
  `demo/expected/dependencies.fixture.json` ("fixture (Noirit scanner not integrated)"). Each
  evidence line is verified against the prepared commit before use.
- **Provider source.** Provider source access is unavailable. Stripe's server implementation is
  not accessible, and the SDKs, stripe-mock and the samples are not provider source.
- **Isolation.** This is a local single-machine demo. It does not prove cross-company identity
  isolation.

## Layout

| Path | Written by | Contents |
|---|---|---|
| `results/` | every pipeline command | Normalized, deterministic documents. These are the reference results. |
| `runs/<run_id>.json` | prepare, execute, validate-migrations | The same run records with the measured `duration_ms` and a bounded log tail. The tail is at most 4 KB and redacted: Stripe-key-like strings, bearer tokens and local paths are removed. `runs/prepare.<repo>.npm-ci.json` records the `npm ci` install (argv, mode: npm cache only with `--offline`, else cache first). |
| `sources/offline-check.json` | fetch-sources | The offline source-lock checks. `--network` writes `demo/.cache/sources/verification.json`. |

Normalization rules for `results/`:

- `duration_ms` is 0.
- There are no absolute paths. Scratch paths appear as `$WORK_DIR/...` and interpreters as `python` / `node`.
- There is no log text.
- The only timestamp is the fixed snapshot date `2026-10-17T12:00:00Z`, which is also the date of the prepared commits.
- Keys are sorted, with a 2-space indent and UTF-8.

Commit SHAs are reproducible because `prepare` commits with a fixed identity and fixed dates.

## Files in `results/` (shapes)

`results/index.json` lists every file with its `kind`, its `audience` and a description.

Audiences:

- **`consumer_private`**: only the consumer org that owns the repository may see it.
- **`provider`**: the provider's view, which never includes consumer source.
- **`internal`**: contract-shaped backend records. The views are derived from them.

| File | Kind | Shape |
|---|---|---|
| `inventory.json` | `shockwave-demo.inventory@1` | `contract` (repository, commit, path, sha256, byte_size, api_version, license), `counts` (operations, paths, by_method, component_schemas, endpoints, by_reconciliation: computed, never hardcoded), `provider_source_access` (`unavailable`), `endpoint` (GET /v1/payment_intents/{intent}: id, parameters, `response.amount` type + documentation, openapi + docs Evidence), `selected_versions`, `evidence_boundaries` |
| `snapshots.json` | `shockwave-demo.repository-snapshots@1` | `records`: shockwave.v1 RepositorySnapshot[] (id, repository_connection_id, commit_sha, fetched_at, content_hash). `repositories`: name → commit, files, ids |
| `prepare.json` | `shockwave-demo.prepare@1` | per repository: commit, SDK dependency, own-suite outcome and counts, consumer fixture id + sha256 |
| `consumers/<repo>/dependencies.json` | `shockwave-demo.consumer-dependencies@1` | `visibility: consumer_private`, `audience` (consumer org), `source` + `label` (FIXTURE), `dependencies`: shockwave.v1 Dependency[] with `evidence.revision` bound to the prepared commit, `negative_controls` |
| `change/api-change.json` | shockwave.v1 APIChange | The declared SIMULATED change: units_changed, `structural_breaking: false`, with declared_change evidence (the manifest and the fixture equivalences), openapi evidence and docs evidence |
| `change/detect-changes.json` | `shockwave-demo.detect-changes@1` | `schema_diff_only` (0 changes: the published schema is unchanged), `with_declared_change` (APIChange[]) |
| `change/analysis.json` | shockwave.v1 AnalysisResult | Risks (rules mode). Scenario pointers are `test` evidence minted by the analyzer |
| `verification/plans.json` | shockwave.v1 VerificationPlan[] | One per risk with a bound executable scenario |
| `verification/results.json` | shockwave.v1 VerificationResult[] | `verified_regression` / `not_run`. Each summary starts with the LOCAL RUNNER DOUBLE label. A not_run summary lists the missing evidence |
| `verification/controls.json` | `shockwave-demo.controls@1` | `controls`: `shockwave.control_result.v1` documents (baseline and proposed), each with its cases and recorded requests. Not tied to any risk |
| `verification/observations.json` | `shockwave-demo.observations@1` | Supporting evidence for the potential storage risk: the reporting consumer's own suite run with the simulated proposed fixture data. It never changes the risk's `not_run` status |
| `migrations/validation.json` | `shockwave-demo.migration-validation@1` | Per migration, details below |
| `consumers/<repo>/findings.json` | `shockwave-demo.consumer-findings@1` | `risks` (each with category, severity, confidence, locations, explanation, suggested_action, `verification`, `migration`, the full Risk), `unresolved`, `unaffected` (listed separately, with the reason), `negative_controls`, `controls`, `observations`, `labels` |
| `provider/restricted-summary.json` | `shockwave-demo.provider-restricted-summary@1` | `consumers`: one entry per pseudonymous label (`Consumer 1..n`) with counts `by_category`, `by_severity` and `by_verification_status`. `totals`, `privacy.excluded`, `isolation`. It contains no file names, paths, lines, snippets, logs, patches, commit SHAs, consumer ids, or org or repository names |
| `runs/<run_id>.json` | `shockwave-demo.run-record@1` | Fields listed below |
| `index.json` | `shockwave-demo.results-index@1` | file → kind / audience / description |

Each migration in `migrations/validation.json` records:

- the patch path and its sha256;
- `patched_proposed`: validated within the tested scope, with the pinned caveat;
- `deployment_assumption`: the patched code against the baseline fixture. It is an expected failure, `is_regression: false`;
- `own_suite`: the consumer's own suite on the migrated copy;
- `scope`: the files changed match the declaration, and the unrelated conversions and negative controls are unchanged;
- `deployment_caveat`.

Each run record in `runs/<run_id>.json` has these fields:

- `run_id`, `stage`, `purpose`, `runner`, `repository`;
- `commit_sha`: the source revision;
- `scenario_id`, `phase`;
- `fixture`: fixture_set_id, path and sha256. This is the fixture revision;
- `patch`;
- `command`: argv and cwd;
- `exit_code`, `timed_out`, `infrastructure_error`, `tests_run`;
- `outcome`, `reason`;
- `assertions`: per case, the expected and actual values, the status and the recorded requests;
- `duration_ms`.

Run ids:

- `prepare.<repo>.own-suite`
- `execute.<scenario>.<baseline|proposed>`
- `control.<scenario>.<variant>`
- `execute.<repo>.own-suite-proposed-fixture`
- `migration.<id>.<patched-proposed|patched-baseline|own-suite>`

## Interpretation rules (from `verification.scenarios`)

- **Verified regression.** A `verified_regression` needs both of these:
  - The baseline passes every case.
  - On the proposed fixture, the relevant case fails while every guard case passes, and the
    preconditions hold: each case requested exactly its own `GET /v1/payment_intents/<id>`, with
    `Stripe-Version: 2026-09-30.endive` and a test-mode key.
- **Inconclusive.** All of these are inconclusive and are never a verified regression:
  - baseline failures;
  - zero tests;
  - infrastructure errors;
  - timeouts;
  - a missing or tampered report;
  - a failing guard.
- **Risks with no executable scenario.** These stay `not_run`, and the result lists the missing
  evidence. In this demo that is the reporting ledger's storage risk.
- **Patched runs.** A patched run that passes is validated within the tested scope only. The
  patch is pinned to the proposed contract. The same patch fails against baseline responses, and
  that run is recorded as deployment-assumption evidence, never as a regression.
